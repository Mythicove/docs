## 结论

建议把 Mythicove 的部署站点做成以玩家和服务器为中心的社区入口：玩家能找到服务器、准备客户端、管理身份、浏览地图；站长能配置连接、管理运行状态和发布内容。Compass 使用 grasscn 建立明确的游戏界面语言；Web 使用现代内容布局，通过世界截图、皮肤、地图和少量 MC 控件表达风格。

这是一份待确认的实施建议，评估日期为 2026-11-09。组件库替换、服务器连接及地图集成尚未在本轮实现。

## 1. 评估依据与当前状态

已阅读当前 Web 首页、导航、主题、后台入口、站点配置，Compass 外壳、首页、样式、依赖和 Tauri 配置，以及项目设计文档、产品规划和 Mirror 路由组装代码。已用浏览器访问本地 `http://localhost:3101/`、太学站和 grasscn 首页并查看截图。后台登录态及完整启动器交互本轮未做运行验收；本地运行版本也未与工作树逐文件核对。

现有 Web、Compass 和 docs 均有未提交的开发内容。评估以当前工作树为准，不能直接沿用旧进度台账中的“尚未接线”等判断。

### 造成 demo 感的具体因素

| 观察 | 代码或运行依据 | 改造方向 |
|---|---|---|
| 部署站首页仍在介绍实现技术 | `web/src/app/[locale]/page.tsx` 首屏以 Yggdrasil API、上传和接入步骤为主 | 首屏回答“这是什么社区、能玩什么、怎样加入”；接入文档移到指南 |
| 真实内容不足 | 首页展示固定 `/skins/steve.png`；本地预览是大块纯色角色，下面主要是功能说明 | 使用站点自己的世界截图、精选皮肤、公告、服务器状态和版本发布 |
| 布局面积与信息量不匹配 | 大尺寸 hero、三步说明和大面积低信息卡片 | 按内容密度分配空间，列表、状态条、作品展示各用合适的结构 |
| 后台导航难以扩展 | `admin/client.tsx` 同级排列 12 个标签 | 左侧分组导航，具体模块有独立 URL、标题和操作区 |
| 启动器首页缺少核心动作 | `compass/src/views/home.tsx` 是登录、皮肤预览和实例概览；首屏没有启动动作 | 当前实例与启动按钮成为主要操作，登录进入账号区 |
| 视觉规范分叉 | 设计文档和 Compass 仍为蓝紫，Web 工作树已改为草绿与石墨 | 先确认品牌规范，再统一变量与组件用法 |

现有的会话、OIDC、皮肤分发、Modrinth 兼容读接口、`.mrpack`、国际化及管理 API 都可继续作为产品基础。视觉改造应围绕真实使用流程展开。

## 2. 太学站值得借鉴的设计

实际访问的太学站是建筑社区门户，包含玩家作品、世界、教程、皮肤和进服入口。它能提供的参考比单一皮肤站更广。

- **以世界和作品作为视觉主体。** 大幅作品截图、创作者署名、作品入口直接说明社区的价值。
- **行动距离短。** 服务器状态、Java/基岩版地址、版本建议和群聊入口靠近作品区。
- **不同内容使用不同结构。** 图片展陈、横向状态带、教程图文和页脚导航并不全部装进同一种卡片。
- **界面承载真实身份。** 玩家头像、人物模型和创作者信息让页面具有社区感。

Mythicove 可借鉴这些组织方式，使用部署者自己的素材与内容。欢迎动画、自动轮播和长页面动效不作为首版必需品；本轮完整页面截图中，部分滚动触发区尚未显现，不能据此评价所有下方页面的视觉完成度。

### 官网与部署站分工

Mythicove 产品官网适合介绍套件、部署方式和协议兼容性；站长部署出来的网站应优先展示自己的社区、玩家与服务器。仅部署皮肤模块时，首页应是皮肤内容与个人衣柜入口；配置服务器后，再出现进服、状态与地图区域。根据已有配置和内容决定区域是否出现，避免额外增加一套首页模式开关。

## 3. 视觉方向：现代布局，Minecraft 内容与交互

### 品牌基线必须先统一

`design/tokens.md` 明确记录蓝紫品牌，但 `web/src/lib/themes.ts` 与 `globals.css` 已采用绿色中性方案；Compass `App.css` 仍保留旧色。本文不把任何一端的现状当作已确认的新规范。

建议优先保留已有品牌辨识度，在同一版视觉稿中比较蓝紫品牌与当前绿色实现，再确认唯一规范。若按当前文档执行，以下六个值可直接作为草图基线，不另造一套色板：

| 角色 | 文档既有值 |
|---|---|
| 品牌主色 | `#4F46E5` |
| 品牌辅助色 | `#8B5CF6` |
| 浅色背景 | `#F8FAFC` |
| 浅色文字 | `#0F172A` |
| 深色背景 | `#0B1026` |
| 深色表面 | `#1A1F3A` |

这些是草图用的部分 token；完整的文本、边框、状态色和交互对比度沿用完整语义体系。绿色表达在线、成功及部分 MC 材质，不因“Minecraft”就强制把品牌改绿。grasscn 自带的原版控件材质作为组件视觉，不整体覆盖品牌色。

### 排版和材料

- 正文沿用 Inter 与系统中文字体栈，标题沿用 Space Grotesk 与中文回退。中文正文不强制位图字体。
- Web 使用清晰分栏、细分隔、紧凑工具栏与足够的内容留白；对话框、浮层、内容容器按功能区分层级。
- 文档原定圆角为 6/10/16px，Web 工作树已有 4/6/8/12/16px；正式视觉稿需与颜色一起收敛，不能继续在页面内各自决定。
- MC 风格主要来自真实世界截图、皮肤、玩家头像、方格选中态、原版按钮和进度条。
- 像素材质重点用于游戏动作和局部框架。日志、长表格、说明文本保持易读；不为每个区块叠加泥土底纹和立体描边。

### Web 首页建议

内容左对齐，桌面宽度围绕现有 `max-w-6xl` 做视觉稿；移动端按同一优先级纵向排列。

```text
站点品牌    服务器  皮肤  模组/整合包  指南       账号
─────────────────────────────────────────────────
真实世界截图 / 精选作品      社区名称与简短介绍
                           加入服务器  下载启动器
─────────────────────────────────────────────────
服务器列表：可连接状态、人数、地址、版本、检查时间
─────────────────────────────────────────────────
公告与最近更新                 我的玩家 / 登录入口
精选皮肤或作品                 对应服务器整合包
地图预览与进入世界地图
─────────────────────────────────────────────────
社区链接、帮助、站点与法务信息
```

未配置服务器时显示皮肤与资源内容；没有作品时不制造虚假精选和人数。后台首次配置引导站长添加封面、介绍和连接，前台依靠已有内容保持紧凑。

世界地图应有独立的大面积浏览页，首屏只放轻量截图和入口，不同时初始化多个 WebGL 地图及角色预览。

### 管理后台建议

```text
概览
社区：公告 / 用户与玩家 / 邀请 / 审核
服务器：服务器列表 / 服务器详情
内容：皮肤 / 模组与整合包
集成：MCSManager / 地图连接
站点：品牌 / 注册与登录 / OAuth 客户端
审计
```

导航只出现已启用的能力。服务器详情以状态、启动/停止/重启、近期日志为主；连接配置与玩家可见信息分开编辑。

### 设计自检

初稿若只是“大标题 + 默认角色 + 三张能力卡”，即使换成 grasscn 也没有解决当前问题。新稿应在首屏就出现站点自己的世界、可加入的服务器或可浏览的皮肤，且主按钮与实际任务一致。把视觉重点放在世界内容，周围导航与工具保持安静。

## 4. Compass 采用 grasscn 的评估

### 适配结论

推荐采用。grasscn 是 MIT 许可、基于 shadcn registry 的 React 组件源码分发方案，包含 Base UI 交互原语和 Minecraft 材质；它并非安装一个包后替换 Provider 的传统组件库。

Compass 目前没有独立 UI 库：主要依赖 React、自写 `App.css` 与原生表单控件。迁移实质是建立组件层、改造布局与样式。现有 Rust 启动、安装和账号能力仍通过原有 IPC 接入。

| 方面 | 现状与工作 |
|---|---|
| React | Compass 为 React 19，方向相符；逐项核对组件实际依赖 |
| 样式构建 | Compass 尚未配置 Tailwind/shadcn；需添加 Tailwind 的 Vite 集成、路径别名和 registry 配置 |
| 基础依赖 | 按选用项添加 Base UI、CVA 等，避免整套示例站依赖进入启动器 |
| 原生控件样式 | 当前全局 `button/input/select` 会影响新组件，迁移期间需收窄选择器，迁移完成的旧规则一起移除 |
| 使用契约 | grasscn Button 当前默认 400×40 浏览器像素，`scale` 为 1/2/3；不能假定支持现有 Web 的所有 variant/size |
| 中文与缩放 | Button 有 Unicode 路径，但已声明的像素验证覆盖有限；真实长中文、输入法、125%/150% DPI 仍需实测 |
| 音效与离线 | Button 自带点击音效；需核对资产引用方式与 Tauri CSP，保证离线可用、重复点击可控、用户可静音 |
| 皮肤预览 | grasscn Player Preview 使用 WebGL2，文档限定调用方皮肤为 64×64；已有 skinview3d 不应因视觉迁移立即替换 |

`PlayerPreview username` 会请求第三方 mc-heads，不能代表本站 Yggdrasil 身份；若之后采用，应显式传入本站控制的纹理。既有皮肤/披风、旧版纹理及加载错误体验须逐项比较。

本轮抓取的 Button registry JSON 含大量配套内嵌资产，总文档超过 2MB；这是源码分发体积，不能当成最终 bundle 大小。原型应测量实际构建结果、字体/资产去重和 WebView 加载表现。

### 推荐迁移顺序

1. 先将 Button、Input、Select、Tabs、Dialog、Progress 等首页及实例页真正需要的组件复制到 `compass/src/components/ui/`，记录来源版本，保留许可和资产来源说明。
2. 完成一条真实的“选账号 → 选实例 → 启动 → 查看进度/失败原因”交互，先验证中文、WebView 与窗口尺寸。
3. 统一实例、内容、日志与设置页，逐页替换旧规则。仅为项目业务建立组合组件，不额外包装每个基础控件。
4. 再考虑 Hotbar 等特色组件；有明确导航含义时使用，不将所有桌面操作硬塞进九个槽位。

### 启动器首页建议

```text
侧栏             当前站点 / 服务器                  账号
开始游戏         世界截图、服务器状态与公告
游戏实例         当前实例、MC / Loader / 整合包版本
内容             缺失内容与下载进度
日志             [启动游戏]  实例选择
设置             次要区域：皮肤预览、最近更新
```

视觉上可以比 Web 更接近原版 MC 菜单，但启动和安装仍是明确的桌面任务。日志等高密度区域不强制位图字体。迁移验收至少覆盖默认 1200×800 与最小 960×640 窗口、长中文、键盘操作和三平台 WebView；不能用普通浏览器成功代替 Tauri 验收。

## 5. 生态整合：以“服务器”为共同入口

服务器应成为一个可以关联公开地址、运行实例、地图和客户端整合包的领域对象。多个世界可以属于同一服务器，代理网络也可能对应多个运行实例；首版不把世界、服务器和进程实例视为同一个 ID。

建议启动既有规划中的 **Isles**，先做小型、可选的 Go 集成服务，承接服务器信息、状态采集与 MCSManager 调用。首版一个服务、一个明确支持的 MCSManager 版本范围，不先建设通用插件框架。代价是服务器整合部署增加一个进程；收益是避免将进程管理和轮询直接塞进负责身份的 Mirror，或依赖 Next 请求生命周期维护采集任务。

```text
Web / Compass ──公开服务器 API──→ Isles ──Java SLP──→ 游戏入口
      │                            └─管理 API────→ MCSManager
      ├─账号/皮肤────────────────→ Mirror
      ├─模组/整合包──────────────→ Hoard
      └─地图页──────────────────→ BlueMap（网关或独立地图域名）

Mirror OIDC ──站点管理员身份──→ Isles
           └─可选面板登录────→ MCSManager
```

Isles 管理侧采用现有 OIDC RP + 本地会话模式，以 `sub` 关联身份；角色由 Isles 自己管理，沿用已有“权限不隐式继承”的原则。公开状态接口不要求玩家先登录。不要将 Web 会话 cookie 原值直接当成其他服务的登录凭据。

### 最小模型与配置体验

首版支持一个 MCSManager 连接及其多个实例，不暴露 provider 类型下拉和手填 JSON：

- **连接**：面板地址、服务端保存的 API key；是否已配置、最后连通结果。
- **服务器**：名称、介绍、封面、Java 公开连接地址；可选绑定一个 MCSManager 实例、一个确定版本的整合包及地图入口。
- **状态快照**：进程状态、游戏探测结果、人数、版本、采集时间与采集错误；按来源保留新鲜度。

地址与密钥是站长输入；节点、实例 ID、面板返回的实例名由系统查询并提供选择。绑定实例后仍需确认玩家实际使用的公开地址，因为面板内网地址、代理地址和玩家入口不一定相同。

### MCSManager 接入流程

1. 后台“集成 → MCSManager”填写面板 URL 和 API key，点击测试。
2. 后端连接 **Web 面板 API**，查询节点和实例，显示可选择对象。
3. 创建服务器条目，绑定实例，填写玩家连接地址，按需关联整合包和地图。
4. 后台详情提供启动、停止、重启、命令和近期日志；前台只返回公开服务器信息与状态。
5. 操作提交后展示执行中，后续采集确认状态；请求受理不等于服务器已经可连接。

已核实的官方接口包括：

| 能力 | 上游接口 |
|---|---|
| 实例列表 | `GET /api/service/remote_service_instances` |
| 实例详情 | `GET /api/instance` |
| 启动 / 停止 / 重启 | `/api/protected_instance/open`、`stop`、`restart` |
| 发送命令 | `/api/protected_instance/command` |
| 近期日志 | `GET /api/protected_instance/outputlog` |
| 实时流通道 | `POST /api/protected_instance/stream_channel` |

官方接口使用 `apikey` 查询参数及指定请求头，API key 权限等于对应账号权限。Mythicove 自己的状态变更端点使用 POST；密钥只在后端使用，不出现在浏览器请求、公开站点配置或未脱敏日志中。后台保存的密钥需可更换、只回传“已配置”，密文与加密主密钥分离保管。

只允许管理预先绑定的实例，每次操作做服务端授权并记录操作者、目标及结果；这也是 API key 代理应有的权限边界。连接允许站长配置私网地址，不能一概禁止私网，但普通玩家不能把探测接口当作任意主机扫描器。

第一版近期日志可用有长度上限的 HTTP 日志接口。实时控制台需要验证目标版本的 Socket.IO 通道、临时凭证和 daemon 网络可达性，属于独立交付项。首次接入不要求复制完整文件管理、备份和定时任务页面。

### 状态语义与采集

- MCSManager 的 running 表示进程运行，不能直接等于玩家可连接。
- 游戏入口用 Java Server List Ping；代理网络探测玩家实际连接的代理入口。基岩版状态是独立协议，后续接入时明确区分。
- 人数、版本、MOTD 可以来自 SLP，玩家列表只是可能存在的 sample，不能宣传为完整在线名单。
- TPS/MSPT 不由普通 SLP 提供；需要明确的数据源，例如兼容的服务端插件或模组。
- 推荐小站先以约 15–30 秒节奏采集并缓存，前台显示检查时间；请求失败显示“暂时无法确认”或过期信息，不把旧值冒充实时状态。
- 延迟标注为站点探测延迟，不能代表玩家所在地的网络延迟。
- 多副本部署指定一个采集执行者或采用已有分布式协调能力，避免副本数乘以采集频率。

### MCSManager 的统一登录

当前官方文档已有 OIDC/OAuth2 SSO 配置，Mirror 可作为候选 IdP，对接 `openid profile email`、`sub` 和固定回调地址。具体最低兼容版本、账号绑定和角色策略需要真面板验证。

“从 Mythicove 后台调用面板 API”与“用户能单点登录 MCSManager”是两条独立链路。先交付站长管理及前台状态，再做可选的面板 SSO，避免为看状态而强制建立 MCSManager 玩家账号。

## 6. BlueMap 分层接入

### 第一层：可使用的地图入口

在服务器下配置地图入口，站点提供独立地图页与全屏/新窗口入口。优先复用 BlueMap 自己的渲染器；静态资源、地图块和实时数据由 Caddy 等网关服务，不经过 Go/Next 转发每个 tile。

BlueMap 官方支持子路径反代和子域名部署。当前 Web CSP 的 `frame-src` 未放行外部地图域名，需按确定的地图来源配置；地图响应自身的 `frame-ancestors`/X-Frame-Options 也必须允许目标站点嵌入。Web 页面自身的 X-Frame-Options 控制它被嵌入，不是它加载地图的许可。

公开地图可直接提供入口；仅成员可见的地图需要在地图及其数据入口统一执行登录鉴权，不能只隐藏导航按钮。若需要隔离第三方扩展脚本与站点会话，可采用独立地图源并在网关验证访问。

### 第二层：世界、地点与皮肤关联

- 在站点展示世界列表、地标和作品说明，点击时通过 BlueMap URL anchor 定位到地图位置。
- 复用官方 marker 配置或 BlueMap API 扩展地标，不假定存在通用的远程 HTTP 写标记接口。
- BlueMap 默认皮肤下载源是 Mojang；离线/Yggdrasil 玩家皮肤不会因嵌入页面自动变成 Mirror 皮肤。需针对部署版本验证 BlueMap 扩展、皮肤资产生成及 UUID 对应方式。
- 地图公开玩家位置遵循 BlueMap 已有的隐藏与发布配置，站点不另行旁路读取和展示隐藏玩家。

### 第三层：确有需求时增加轻量 Bridge

需要可靠的游戏 UUID 绑定、完整在线玩家、TPS/MSPT、白名单申请自动执行或双向事件时，再提供适配目标服务端的 Bridge。先选实际用户的 Paper 或 Fabric 一条实现路径，而非同时维护所有 loader。

账号使用 Mirror 的 OIDC `sub`，游戏身份使用经验证的 UUID，服务器用 Isles ID；不要用玩家名或邮箱串联所有系统。正版 UUID、离线 UUID 与本站 Yggdrasil UUID 可能不同，绑定必须验证游戏内控制权，不能靠同名推断。Bridge 也不让任意网页内容直接成为控制台命令。

## 7. 值得优先深化的其他联动

后续扩展调研见[自部署站点的可选 Minecraft 生态整合](./optional-mc-integrations.md)，覆盖内容同步、权限、玩家统计、性能、领地、任务与治理工具，并区分远程接口、分发格式和需要 Bridge 的游戏内 API。

| 方向 | 用户可感知的结果 | 次序 |
|---|---|---|
| Hoard + `.mrpack` + Compass | 服务器指定客户端包及版本，启动器安装/更新并连接正确地址 | 高，先利用已有能力 |
| MCSManager | 站长在本站完成常用操作，玩家看到可信的连接状态 | 高 |
| BlueMap | 进服前可看世界，站点作品与地图位置关联 | 高 |
| Paper/Fabric Bridge | 游戏内绑定、白名单、完整人数及性能数据 | 在首批集成稳定后 |
| Velocity / Geyser / Floodgate | 正确描述代理网络和跨版本/跨平台入口与身份 | 根据真实部署推进 |
| LuckPerms | 把已验证的成员资格映射到指定游戏权限组 | 在账号绑定可靠后 |
| Discord / QQ / Webhook | 公告、维护和版本更新通知 | 按社区实际渠道推进 |
| Dynmap / squaremap / 其他面板 | 有第二个真实接入需求后再提炼共同接口 | 后续 |

“进入服务器”最终可形成：选择服务器 → 获取指定包版本 → 检查 Java/Loader/内容 → 以正确身份启动并连接。网页唤起 Compass 的自定义协议目前未在所读 Tauri 配置中声明，不能把已有 CLI 与 `.mrpack` 文件关联当作已完成的网页唤起。

首次安装可以先用 `.mrpack` 下载和已有文件关联；后续增加深链时只携带站点认可的服务器/包标识，启动器从可信 API 解析，不接收任意本地执行参数。

## 8. 分阶段交付与验收

| 阶段 | 最小交付 | 验收结果 |
|---|---|---|
| A：视觉基线与真实原型 | 确认品牌，Web 首页/服务器页/后台详情/Compass 首页设计；Compass 引入必要 grasscn 组件 | 真实长中文、最小窗口和三平台 WebView 可用；启动与错误流程完整 |
| B：社区门户 | 内容驱动首页、后台分组导航、服务器公开页面、Java SLP 状态采集 | 无 MCSManager 也能展示可信游戏状态；过期/失败有明确表达 |
| C：MCSManager | Isles 管理会话、单连接配置、实例选择、启停重启、命令、近期日志及审计 | 真面板完成连接→绑定→控制→状态确认；普通用户无法操作未授权实例 |
| D：地图与客户端准备 | BlueMap 页面、网关部署说明、服务器绑定确定版本整合包、Compass 安装入口 | 地图资源与访问控制正确；新玩家按页面指引能安装匹配客户端并进服 |
| E：深入游戏 | 按需要交付 Bridge、游戏内身份验证、白名单或性能数据 | 真实目标服务端完成游戏与网页双向流程，再扩展其他插件 |

实时日志流与面板 SSO 可以在 C 的常用管理链路完成后分别交付。每阶段独立可用，不等待全部生态能力到齐。

现有首页声明 `force-static`，加入状态后应保留可缓存的站点内容并独立加载动态状态，或明确采用适合的新渲染策略，不能把构建时人数当作实时人数。公开 API schema、生成客户端与现有漂移检查随新增能力一起维护。

## 9. 方案复杂度检查

1. **结构性**：以服务器贯穿状态、地图和整合包，解决各模块只提供独立入口的问题。
2. **配置负担**：增加的必要输入是面板地址/密钥、玩家公开地址和可选地图；实例 ID、节点信息及状态由系统获取。
3. **可推导信息**：模块导航按实际能力与内容生成，不另设首页模式、provider 选择和手填状态字段。
4. **规模**：先做一个具体 MCSManager 适配、缓存状态与地图入口，不建设插件市场、通用事件总线或新的权限 DSL。
5. **扩展性**：模型区分服务器、进程和世界，接第二个真实上游时再决定共享哪些接口。

最小有效改造包含一个真实的 Compass 主流程，以及一个能把玩家带入游戏的 Web 服务器页。单换按钮无法提供缺少的内容和生态关联；先建设覆盖所有 MC 插件的框架则超过当前需要。

本轮只新增此评估文档，产品代码未修改。后续正式视觉稿确认后再修订 `design/tokens.md`、`visual-rules.md` 和相应产品计划，避免将建议提前写成既定架构。
